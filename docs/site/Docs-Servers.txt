01
The serve model

Executable

Every transport publishes 
one tool / skill per declaration
 found under the directory (default 
.
). Each derives its input contract from the workflow's 
input name: Type
 declarations — every input required, unknown inputs rejected — and its description from an optional 
description: "..."

Transport

02
Try it with the sample

Executable

Save these four self-contained workflows (no real LLM needed) into a 
workflows/
 directory — every example on this page serves that directory.

Copy

// workflows/summarize.mh
agent Writer {
    command: "echo"
    args: ["${prompt}"]
}

workflow Summarize {
    description: "Summarize a topic in at most `max_words` words."
    input topic: string
    input max_words: number
    var summary = ""
    step Draft { summary = Writer.run(prompt: "Summarize ${topic} in ${max_words} words.") }
}

// workflows/triage.mh
workflow Triage {
    description: "Classify an incoming issue as normal or urgent."
    input title: string
    input body: string
    var priority = "normal"
    step Classify {
        if (title.contains("outage") || body.contains("down")) priority = "urgent"
    }
}

// workflows/report.mh — four ~1s steps, so run/status visibly advances
workflow Report {
    description: "Four-step report pipeline (gather, analyze, summarize, publish)."
    input topic: string
    var gathered = ""
    var analysis = ""
    var summary = ""
    var published = ""
    step Gather    { gathered = cmd.exec(["sh", "-c", "sleep 1; echo notes on ${topic}"]).stdout }
    step Analyze   { analysis = cmd.exec(["sh", "-c", "sleep 1; echo analyzed"]).stdout + " " + gathered }
    step Summarize { summary = cmd.exec(["sh", "-c", "sleep 1; echo summary of ${topic}"]).stdout }
    step Publish   { published = "published: " + summary }
}

// workflows/approval.mh — the human-in-the-loop gate
workflow Approval {
    description: "Prepare, wait for human approval, then finish."
    input request: string
    input approved: string          // "no" on start, "yes" on resume
    var summary = ""
    step Prepare { summary = "ready to act on: " + request }
    step Gate {
        if (approved != "yes") pause("awaiting approval for: " + request)
    }
    step Act { summary = "acted on: " + request }
}

Copy

mhl lint ./workflows

mhl serve mcp ./workflows          # stdio
mhl serve mcp --http ./workflows   # http://127.0.0.1:8711/mcp
mhl serve a2a ./workflows          # http://127.0.0.1:8710/

03
MCP over stdio

Executable

mhl serve mcp <dir>
 speaks newline-delimited JSON-RPC 2.0 on stdin/stdout — the form an MCP client uses when it spawns the server as a subprocess. One tool per declaration; 
tools/call
 returns the final variable state (
isError: true
 on a run failure). Diagnostics go to 
stderr
; stdout is the raw protocol stream.

Initialize, list tools, and call a workflow

Copy

printf '%s\n' \
  '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18"}}' \
  '{"jsonrpc":"2.0","id":2,"method":"tools/list"}' \
  '{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"Triage","arguments":{"title":"api outage","body":"everything is down"}}}' \
| mhl serve mcp ./workflows

OWNERSHIP

Each run is owned by the session (
Mcp-Session-Id
) that started it. 
mhl_run_status
, 
mhl_run_resume
, 
mhl_run_cancel
 and 
mhl_run_list
 only act for that caller — any other sees 
unknown runId
 (the same answer as a genuinely unknown id, so it is not an existence oracle). Stateless callers have no session and share one anonymous owner, so stateless mode has no per-caller isolation. Terminal runs stay pollable for an hour; a server shutdown cancels any still running.

RAW METHODS

Each 
mhl_run_*
 tool is a thin bridge over a same-named custom JSON-RPC method — 
run/start
, 
run/status
, 
run/resume
, 
run/cancel
, 
run/list
,

 / 
{runId}

 envelope. Reach for those only when a policy gateway must match one method by name (
POST /mcp/run/resume
); from an ordinary MCP client, use the tools. Every per-workflow 
tools/list

_meta.mhl.run.tool: "mhl_run_start"

INPUT LIMITS

The 
runId
 from 
mhl_run_start
 is durable from that call — it is a real id, not a placeholder that a later step upgrades, and there is no separate claim id. 
arguments
 for 
mhl_run_start
 and

06
Human-in-the-loop: 
pause()
 + 
mhl_run_resume

Executable

A gate step calls 
pause("...")
 to hand off to a human: the run parks in 
state: "paused"
 — not failed, not completed — 
resumable
, with the reason and the vars-so-far in its status, and its state kept (unlike a completed run). 
mhl_run_resume
 with 
{runId, arguments}
 re-enters that same step, merging 
arguments
 over the originals — that is where the approval decision goes. 
pause()
 writes its own checkpoint, so no 
checkpoint {}
 block is required; a step that calls 
fail("...")
 instead lands in 
state: "failed"
 and needs 
checkpoint { strategy: "per_step" }
 to be resumable.

Approval workflow

Copy

workflow Approval {
    description: "Prepare, wait for human approval, then finish."

    input request: string
    input approved: string   // "no" on mhl_run_start, "yes" on mhl_run_resume

    var summary = ""

    step Prepare { summary = "ready to act on: " + request }

    step Gate {
        if (approved != "yes") {
            pause("awaiting approval for: " + request)
        }
    }

    step Act { summary = "acted on: " + request }
}

ACROSS A RESTART

Start the server with 
--state-dir <dir>
 (or 
MHL_SERVE_STATE_DIR
) and a later process pointed at the same directory can 
mhl_run_status
 / 
mhl_run_resume
 a 
runId
 it never started — the first caller to name the (unguessable) id reclaims it. Without it, run state is per-process and lost on restart. Checkpoints are one small JSON file per completed step, sized by the pipeline's variable state; 
mhl_run_status
 on a live run stays a pure in-memory read.

MULTIPLE REPLICAS

When several server processes share one 

extension store

 that advertises the 
cas
 capability (atomic compare-and-swap), each run is guarded by a short-lived lock in the store: exactly one replica executes or resumes a given 
runId
 at a time, renewed on a heartbeat (~1/3 of the lease TTL). The lease TTL defaults to 45 s; widen it with 
MHL_SERVE_RUN_LOCK_TTL
 on a CPU-contended host so a slow renew is not mistaken for a dead replica. Each acquisition is tagged with a token, so a replica whose lease lapsed and was taken over cannot renew or release the successor's lock. A confirmed lease is required to start: if the store cannot be reached to take the lock the run 
fail
s (
"could not acquire run execution lease"
) rather than running uncoordinated, and a 
run/resume
 whose lock state can't be read is refused. If a replica dies, its lock lapses after the lease TTL and 
run/status
 reports the run 
failed
 with 
resumable: true
 — recovery is an explicit 
run/resume
 on a live replica, never automatic; the running replica also cancels its own work if its renewals fail for long enough that the lease is about to expire. A store 
without

cas
 makes the server 
refuse to start
 unless you pass 
--single-replica
 (or set 
MHL_SERVE_SINGLE_REPLICA
) to acknowledge a one-writer deployment; a plain 
--state-dir
 with no 
extension store
 is unaffected. This lock stops two replicas from 
starting
 work on the same run, and checkpoint writes are fenced on the lease — with a store that advertises 
fence
 (e.g. PostgreSQL) a checkpoint write is one atomic statement conditioned on the lease still being this replica's, so a replica taken over after a stall has the write 
rejected by the store
; without it, a check-then-write with a narrow race. Each replica also runs a periodic housekeeping sweep (every 60 s) that reaps idle sessions and, on a shared store, deletes the records of runs that finished more than 
MHL_SERVE_TERMINAL_RUN_TTL
 ago — so the store does not grow without bound. A store that advertises the 
scan
 capability serves the durable-intake reconcile/sweep scans and the 
mhl_serve_runs_pending
 gauge from a single indexed query instead of a per-run read.

08
A2A skills over HTTP

Executable

mhl serve a2a [--addr host:port] [--token t] [--principal-header h] <dir>
 publishes one A2A skill per declaration: JSON-RPC 2.0 over HTTP, with an Agent Card at 
/.well-known/agent-card.json
. 
message/send
 starts a run as a task; 
tasks/get
 polls it and 
tasks/cancel
 stops it. The skill and inputs are named explicitly in the message metadata.

AUTH

Same guard surface as 
serve mcp --http
: 
--token
 / 
MHL_SERVE_TOKEN
 requires 
Authorization: Bearer <token>
 on every JSON-RPC request (the Agent Card stays public for discovery); 
--principal-header
 / 
MHL_SERVE_PRINCIPAL_HEADER
 takes the caller identity from a header an authenticated upstream set, and needs 
--token
 (without the shared secret the header is client-spoofable). A cross-origin browser request (non-loopback 
Origin
) is refused, and the request body is capped at 1 MiB. Binding a non-loopback address with no token prints an "unauthenticated" warning.

Start the server, discover it, and send a task

Copy

mhl serve a2a --addr 127.0.0.1:8710 ./workflows &

  "params":{"message":{"role":"user","parts":[],
    "metadata":{"skill":"Triage","input":{"title":"db outage","body":"prod is down"}}}}}'
# -> { "result": { "id": "<task-id>", "status": { "state": "submitted" }, ... } }

curl -s -X POST localhost:8710/ -d '{"jsonrpc":"2.0","id":2,"method":"tasks/get","params":{"id":"<task-id>"}}'
# -> status.state "completed", artifacts[0].parts[0].text = the run's result JSON
