# Fase 5 — Achados (Servir via MCP local)

> Segue o mesmo espírito de [FASE0-ACHADOS.md](FASE0-ACHADOS.md)/[FASE2-ACHADOS.md](FASE2-ACHADOS.md)/[FASE4-ACHADOS.md](FASE4-ACHADOS.md), escopado à Fase 5.

## 0. Contexto — o que esta fase encontrou pronto, e o que faltava

O spike de Fase 0 (`app/mhlbridge`) já provava o mecanismo (`exec.Command` de `mhl serve mcp --http` em loopback + handshake MCP completo, `ToolsList`/`ToolsCall` genéricos). Faltava a metade "async" real que a Fase 5 pede: `mhl_run_start`/`mhl_run_status`/`mhl_run_resume`/`mhl_run_cancel`/`mhl_run_list`/`mhl_run_logs` tipados, `resources/read` (`mhl://workflow/<nome>`), `--state-dir`, e o polling do lado Go empurrado ao frontend (`runtime.EventsEmit`) em vez de o frontend fazer polling duplicado. Contratos exatos (`{workflow, arguments}` → `{runId, state}`; `structuredContent` como o payload tipado dentro do envelope `tools/call`; `resources/read` → `{contents:[{uri, mimeType, text}]}`) confirmados por spike direto via `curl` contra um `mhl serve mcp --http` real antes de escrever qualquer Go — não presumidos da doc.

**O que essa implementação revelou, e que nenhuma fase anterior tinha testado:** todo teste real de ponta a ponta até aqui (Fases 2-4) rodou `mhl` manualmente, a partir da raiz do repo, como CWD. A Fase 5 é a primeira vez que `mhl` roda com uma CWD **diferente** — o bridge Go precisa que `projects/` viva num diretório de dados do usuário gravável (não dentro do bundle do app, que pode nem ser gravável), não na raiz do repo. Isso expôs **três bugs reais, nenhum deles hipotético** — cada um encontrado rodando de verdade, não por inspeção de código.

## 1. Achado crítico — o caminho do schema do Codex (`--output-schema`) quebra assim que a CWD de `mhl` não é mais a raiz do repo

`*SchemaFile.get().path` (ex. `"workflows/shared/schemas/brief.schema.json"`) é uma string relativa hardcoded, passada como argumento cru pro `codex` CLI via `--output-schema ${schema}`. `codex` é um **subprocesso separado**, que resolve esse caminho relativo contra a **sua própria CWD** — herdada da CWD do `mhl` que o spawnou, nunca do `.mh` que declarou a string (mesma classe do achado de Fase 2 sobre `fs.read` resolvendo contra CWD, não contra o arquivo declarante — [FASE2-ACHADOS.md §2](FASE2-ACHADOS.md#2-achado-crítico-de-arquitetura--fsread-resolve-contra-o-cwd-do-processo-prompt--from-arquivo-resolve-contra-o-diretório-do-mh-que-declara) — só que ali era o próprio `mhl` lendo um arquivo; aqui é um argumento de linha de comando repassado a um processo filho).

Enquanto `mhl` sempre rodou com CWD = raiz do repo (todo `mhl run` manual desta e das fases anteriores), `"workflows/..."` resolvia certo por coincidência — nunca foi testado com outra CWD até o bridge Go apontar `cmd.Dir` pro diretório de dados do usuário. Reproduzido de verdade: `Failed to read output schema file workflows/wiki/schemas/ingest.schema.json: No such file or directory`.

**Correção:** `tool WorkflowsRoot` (`workflows/shared/workflows_root.mh`) — todo `*SchemaFile.get().path` passa a montar o caminho via `WorkflowsRoot.resolve(relative)`, que lê `env("SENPAI_WORKFLOWS_ROOT")` (setado pelo bridge Go, absoluto) e monta um caminho absoluto quando presente; cai no literal `"workflows/" + relative` de sempre quando ausente (uso manual via CLI — nenhuma regressão nas Fases 2-4). `env(...)` usado assim, como expressão comum dentro de um `tool`, devolve `""` pra var ausente sem lançar erro (confirmado por spike) — diferente do comportamento de `env(...)` **dentro de `agent.command`/`args`**, ver achado 3 abaixo.

## 2. Achado crítico — Codex recusa rodar fora de um repositório git, e mesmo permitindo, enxergaria `projects/` de TODOS os work-items

Corrigido o achado 1, a chamada ainda falhava: `Not inside a trusted directory and --skip-git-repo-check was not specified` — o diretório de dados do usuário (`~/Library/Application Support/senpai/data` no macOS) não é um repositório git, e o `codex` CLI recusa rodar fora de um por padrão.

Adicionar só `--skip-git-repo-check` teria sido a correção mínima, mas expôs um problema mais sério ao pensar no porquê da checagem existir: sem um `-C/--cd` próprio, o `codex` **herda a CWD do `mhl`** como seu "working root" — que, no bridge, é o diretório de dados **compartilhado por todos os work-items** (`projects/<id>/` de cada um, lado a lado). `--sandbox read-only` restringe **escrita**, não leitura — nada impede o Codex de, em princípio, ler `projects/<outro-id>/...` ao decidir explorar o diretório por conta própria (mesma classe de risco do achado de Fase 0 sobre `claude -p` sem `--disallowed-tools` explorando além do que o prompt pedia — [FASE0-ACHADOS.md §9](FASE0-ACHADOS.md#9-achado-crítico-de-segurança--claude--p-sem-flag-de-restrição-explora-e-escreve-fora-do-escopo-do-prompt)). Isso fura C1/C2 na prática, mesmo que nenhum teste realizado tenha efetivamente disparado uma leitura cross-projeto — o ponto é que nada no design impedia.

**Correção:** `codex exec` aceita `-C/--cd <DIR>` — seu working root, **independente** da CWD do `mhl` que o spawnou. `tool CodexCwd` (`workflows/shared/agents.mh`) resolve esse valor a partir de `env("SENPAI_CODEX_CWD")` (setado pelo bridge Go — `app/mhlbridge.Start`, novo parâmetro `codexCwdDir` — pra um diretório de scratch dedicado, `~/Library/.../senpai/codex-cwd`, sem nenhum dado de projeto dentro, criado vazio e nunca escrito por este pacote), com fallback `"."` quando ausente (uso manual — Codex enxerga a CWD de onde `mhl` foi chamado, mesmo comportamento de sempre). `--skip-git-repo-check` acompanha, já que o diretório de scratch também não é um repositório git.

## 3. Achado de linguagem — `env(...)` usado direto em `agent.command`/`args` é tratado como referência de credencial: falha fechado se ausente, e o valor sai redigido (`[REDACTED]`) de qualquer saída/log do `mhl`

Tentativa inicial pro achado 2: `args: [..., "--cd", env("SENPAI_CODEX_CWD"), ...]` direto no `agent Codex`. Duas surpresas, confirmadas por spike isolado (2 variações mínimas):

- **Sem fallback possível.** Ao contrário de `env(...)` em qualquer outro lugar da linguagem ("An unset variable returns the empty string", Docs-Specification) — dentro de `agent.command`/`args` especificamente, uma var ausente faz o `agent.run(...)` falhar com `environment variable "X" is missing or empty`, não devolver `""`. Não dá pra escrever `if (env("X").is_empty()) "." else env("X")` inline em `args:` por esse motivo (e nem funcionaria de qualquer forma — `if/else` dentro do array literal de `args:` também falha, com `undefined variable "env"`, aparentemente uma superfície de expressão mais restrita ali do que dentro de um `tool` comum).
- **Redaction automática.** O valor que chega através de `env(...)` em `args:` é registrado pro mecanismo de redaction do `mhl` (a mesma proteção pensada pra credenciais reais, ex. `env("API_TOKEN")` em `headers:`) — mesmo sendo, neste caso, só um caminho de diretório, não um segredo. `mhl run --format json` devolveu `"--cd [REDACTED] hi"` num spike mínimo.

**Contornado, não implementado como sugestão de correção:** computar o valor num `tool` comum (`CodexCwd.resolve()`, achado 2) e referenciar a **chamada do tool** como elemento do array `args:` (não uma string com `${...}`, que só interpola os dois placeholders reservados `prompt`/`schema` — ver achado 4) — confirmado por spike que isso funciona sem cair no tratamento de credencial: `env(...)` dentro do `tool` comporta-se normal (`""` pra ausente, sem redaction), só o resultado final (já uma string comum) é que vira o argumento de `args:`.

**Sugestão pro mantenedor do MHL:** documentar explicitamente essa diferença de comportamento de `env(...)` dentro vs. fora de `agent.command`/`args` — hoje só aparece como dois erros de runtime distintos e inesperados, não como um contrato declarado. Se a intenção é mesmo "todo `env()` em config de agente é credencial", vale ao menos permitir um fallback declarativo (`env("X") ?? "default"` ou equivalente) sem perder a redaction pra quem quer isso de propósito — hoje a única saída é sair do mecanismo de credencial completamente via um `tool` indireto, o que também desliga a redaction (aceitável pra um caminho de diretório, não seria pra uma credencial de verdade). Registrado como candidato a item novo do [MHL-Melhorias.md](MHL-Melhorias.md) (não numerado formalmente aqui — achado de fase, ver arquivo pra a entrada oficial).

## 4. Achado de linguagem — `agent.run(...)`/`router.delegate(...)` só interpolam os dois placeholders reservados `${prompt}`/`${schema}` em `args:`; parâmetros extras nomeados na chamada não chegam lá

Confirmado por spike direto (não document ado em nenhum lugar lido): `Agent.run(prompt: "hi", cwd: "/tmp/x")` com `args: ["--cd", "${cwd}", "${prompt}"]` devolve literalmente `"--cd ${cwd} hi"` — `${cwd}` nunca é substituído, mesmo sendo um parâmetro nomeado real passado na chamada. Reforça por que o achado 3 precisou de um `tool` calculando o valor de antemão (uma expressão avaliada na declaração de `args:`), em vez de tentar passar o valor por parâmetro de chamada — esse caminho simplesmente não existe hoje. Já era conhecido que isso vale pra `router.delegate(...)` (raiz do achado que motivou abandonar `router` na correção de agentes descrita em [MHL-Melhorias.md #16](MHL-Melhorias.md)); esta fase confirma que o mesmo limite vale igual pra uma chamada direta `.run(...)`, sem router no meio.

## 5. Achado — `self.<metodo>(...)` não herda variáveis locais do metodo chamador; achado de novo, agora fora de `agent.after`

Já confirmado pra `agent.after` na Fase 4 ([MHL-Melhorias.md #17](MHL-Melhorias.md)): um hook/metodo chamado indiretamente não enxerga as vars locais de quem o chamou, só as suas próprias. Esta fase encontrou a MESMA classe de bug num lugar novo, sem relação com `agent`/`after`: `tool WikiActions` (`workflows/wiki/actions.mh`, extraído numa refatoração paralela a esta fase) tinha `commit_ingest(project_id, data)` chamando `self.log("ingest", data.source_title)` — e `log(action, description)` **não recebia `project_id`** como parâmetro próprio, mesmo `WikiLog.append(...)` (chamado de dentro de `log`) precisando interpolar `${project_id}` no seu `path:`. Falhava com `undefined variable "project_id"` — reproduzido de verdade em **todo** `ingest` (não só em resume/Modo Buddy, onde foi encontrado primeiro; confirmado depois que falha igual num `mhl run` direto, sem pausa nenhuma envolvida).

**Correção:** `project_id` virou parâmetro explícito de `log`/`record_lint`, threaded por toda a cadeia de chamada (`commit_ingest`/`file_answer` → `self.log(project_id, ...)`; `wiki.mh`'s `Lint` step → `WikiActions.record_lint(project_id)`) — mesmo padrão que `Writer.generate` já usava corretamente pra `Usage.append` (Fase 4, [MHL-Melhorias.md #17](MHL-Melhorias.md)).

**Lição, reforçada:** toda `memory` com `path:` interpolado só pode ser tocada (`.append`/`.get`/etc.) de dentro de um método que tenha a variável interpolada como **seu próprio parâmetro** — nunca por herança de escopo via `self.`, nem de um `tool` "vizinho", nem de um hook como `after`. Vale como checklist pra qualquer `tool` novo que envolva `memory` interpolada por `project_id` (ou qualquer outra var) daqui pra frente — `mhl lint` não pega isso (só aparece em runtime, e só quando aquele caminho de código específico é exercitado; por isso passou despercebido até esta fase testar `ingest` de ponta a ponta pela primeira vez depois da refatoração paralela).

## 6. Mecanismo Go implementado (referência rápida, não achado)

- `app/mhlbridge.Client`: `ResourceRead`, `RunStart`/`RunStatusGet`/`RunResume`/`RunCancel`/`RunList`/`RunLogs` (todos decodificando `structuredContent`, confirmado por spike via `curl`), `PollRunStatus` (loop headless, sem nenhuma dependência de Wails — testável fora de um app rodando de verdade).
- `App` (bindings reais, substituindo o `PingMHL` temporário da Fase 0): `ListWorkflows`, `GetWorkflowManifest`, `StartRun`, `GetRunStatus`, `ResumeRun`, `CancelRun`, `ListRuns`, `GetRunLogs`, `WatchRun` (polling do lado Go + `runtime.EventsEmit`, §6.2 do plano).
- **Achado de teste, não de produto:** `runtime.EventsEmit(ctx, ...)` do Wails é `log.Fatalf` (mata o processo) se `ctx` não for o contexto real que o Wails injeta em `OnStartup` — não um no-op seguro fora de um app rodando de verdade (confirmado lendo `wailsapp/wails/v2/pkg/runtime`, `getEvents`). `App.emit` existe como campo trocável (não uma chamada direta a `runtime.EventsEmit`) exatamente por isso — é o que torna `WatchRun` testável em `go test` sem derrubar o processo de teste.
- `--state-dir`/dados do usuário resolvidos via `os.UserConfigDir()` (já multiplataforma — C6 — sem branch por SO própria): `<UserConfigDir>/senpai/{state,data,codex-cwd}`.

## Consequência prática

- `PLANO-MACRO-MHL-SENPAI.md` §5 (Fase 5) e a tabela de status já refletem isso.
- Qualquer fase futura que precise passar um caminho a um subprocesso de agente (não só Codex) deve assumir `WorkflowsRoot`-como-padrão, não `fs.read`/caminho relativo cru — o mesmo problema vale pra qualquer CLI futuro que receba caminho de arquivo por argumento.
- Todo `tool` com um `memory` interpolado precisa de auditoria da mesma forma que `WikiActions`/`Writer` — o checklist do achado 5 deveria virar item de review manual em qualquer fase que adicionar um `tool` novo tocando `memory`.
